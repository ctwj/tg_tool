# Feature Specification: 调度可视化面板

**Feature Branch**: `018-scheduler-dashboard`
**Created**: 2026-06-09
**Status**: Draft
**Input**: User description: "帮我分析一下系统， 下一步做什么最合适"（用户选择"调度可视化面板"方向）— 展示定时任务下次执行时间、历史执行记录、失败重试状态

## 背景与目标

当前系统有两个定时调度器（推送调度 + 提取调度），但它们的运行状态对用户完全不可见：
- 推送调度和提取调度是否在运行、下次什么时候执行，用户无法直观看到
- 调度失败时仅在日志中 `warn`，前端无任何提示，推送可能静默失败数小时无人察觉
- 推送历史虽存在 `push_histories` 表，但前端 Push.tsx 当前未展示下次执行时间和调度运行状态
- 提取任务完全没有批次级历史记录（结果只在日志和 extracted_resources 表中）

本功能目标：在前端提供独立的调度可视化面板，让用户一目了然地看到所有定时任务的运行状态、下次执行时间、历史执行记录和失败情况，从而具备调度运维的可观测性。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 查看调度任务总览状态 (Priority: P1) 🎯 MVP

用户打开调度可视化面板，一眼看到系统中所有定时任务（推送调度、提取调度）的当前状态：任务名称、是否启用（运行中/已停止）、执行间隔、下次执行时间（倒计时）。用户据此判断定时任务是否正常工作，无需查看日志或猜测。

**Why this priority**: 这是面板的核心价值——让调度状态可见。没有这个，用户依然无法判断推送/提取是否在正常运行。

**Independent Test**: 打开调度面板，能看到推送调度和提取调度各自的状态卡片（运行状态 + 间隔 + 下次执行时间），即可验证。

**Acceptance Scenarios**:

1. **Given** 推送调度已启用且间隔为 30 分钟，**When** 用户打开调度面板，**Then** 看到推送调度卡片显示"运行中"、间隔 30 分钟、下次执行时间（绝对时间 + 倒计时）
2. **Given** 提取调度未启用，**When** 用户打开调度面板，**Then** 看到提取调度卡片显示"已停止"、间隔（配置值）、下次执行时间为"—"
3. **Given** 调度面板已打开，**When** 等待一段时间（如下次执行临近），**Then** 下次执行时间和倒计时自动更新（无需手动刷新）
4. **Given** 推送和提取调度都未配置，**When** 用户打开调度面板，**Then** 看到两个调度卡片均显示"已停止"状态

---

### User Story 2 - 查看推送执行历史与成功率 (Priority: P2)

用户在调度面板查看推送任务的历史执行记录列表，包括每次推送的批次 ID、目标、状态（成功/失败）、数据量、消息、错误信息和执行时间。同时看到汇总统计（总次数、成功数、失败数、成功率）。用户据此评估推送任务的长期可靠性，识别频繁失败的时段。

**Why this priority**: 推送历史数据已存在（push_histories 表），只需整合展示，是评估调度健康度的关键指标。

**Independent Test**: 打开调度面板的推送历史区，能看到分页的历史记录列表和顶部统计卡片。

**Acceptance Scenarios**:

1. **Given** 有推送历史记录，**When** 用户打开调度面板推送历史区，**Then** 看到统计卡片（总次数、成功、失败、成功率）和历史列表（批次ID、目标、状态、数据量、时间）
2. **Given** 推送历史为空，**When** 用户查看推送历史区，**Then** 显示空状态提示"暂无推送记录"
3. **Given** 某次推送失败，**When** 用户查看该条历史，**Then** 能看到失败状态标签和具体的错误信息（error_msg）
4. **Given** 推送历史超过一页，**When** 用户翻页，**Then** 列表正确加载对应页的数据

---

### User Story 3 - 查看提取执行历史 (Priority: P3)

用户在调度面板查看提取任务的历史执行记录，包括每次提取的扫描数、成功提取数、跳过数、错误数和执行时间。用户据此监控提取效率，发现提取数量异常下降的趋势。

**Why this priority**: 提取当前无批次历史记录，需新建表持久化。优先级低于推送历史（推送历史数据已就绪），但仍是完整运维面板的必要组成。

**Independent Test**: 触发一次提取后，打开调度面板提取历史区，能看到对应记录。

**Acceptance Scenarios**:

1. **Given** 提取任务已执行过，**When** 用户打开调度面板提取历史区，**Then** 看到提取历史列表（扫描数、提取数、跳过数、错误数、执行时间）
2. **Given** 提取任务从未执行，**When** 用户查看提取历史区，**Then** 显示空状态提示

---

### Edge Cases

- 调度器重启后 `last_run_at` 内存状态丢失：下次执行时间显示应基于"调度启动时间 + 间隔"重新计算，而非显示错误的历史值
- 服务刚启动、调度尚未首次执行时：下次执行时间显示为"启动后约 N 分钟"，倒计时正常递减
- 跨天执行（如下午 11:50 间隔 30 分钟，下次为次日 00:20）：时间显示需正确显示日期
- 推送历史时间显示：后端存的是 naive 本地时间，前端需正确解析，避免时区错乱
- 历史记录数据量很大（数千条）：必须分页，不能一次性加载全部
- 提取历史表首次部署（无数据）：面板正常显示空状态，不报错

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 系统必须提供一个独立的调度可视化页面（或 Dashboard 的独立区块），集中展示所有定时任务状态
- **FR-002**: 面板必须为每个调度任务（推送、提取）展示状态卡片，包含：任务名称、运行状态（运行中/已停止）、执行间隔、下次执行时间
- **FR-003**: 下次执行时间必须同时显示绝对时间（如 2026-06-09 10:30:00）和倒计时（如 12 分钟后），且自动刷新更新
- **FR-004**: 系统必须持久化提取任务的批次执行记录（扫描数、提取数、跳过数、错误数、执行时间），因当前提取无历史表
- **FR-005**: 面板必须展示推送执行历史列表，包含批次 ID、目标、状态、数据量、消息、错误信息、执行时间，并支持分页
- **FR-006**: 面板必须展示推送统计汇总（总次数、成功数、失败数、成功率）
- **FR-007**: 面板必须展示提取执行历史列表，包含扫描数、提取数、跳过数、错误数、执行时间，并支持分页
- **FR-008**: 推送失败状态必须用醒目颜色（红色）标记，便于用户快速识别失败记录
- **FR-009**: 下次执行时间计算必须正确处理服务重启场景（基于启动时间重新推算，而非显示错误的历史值）

### Key Entities

- **PushHistory**: 已存在的推送历史记录（push_histories 表），字段含 batch_id、target、status、data_count、message、error_msg、pushed_at
- **ExtractHistory**: 需新建的提取历史记录，记录每次提取的 total_scanned、extracted、skipped、errors、executed_at
- **SchedulerStatus**: 调度任务运行状态，含 running、interval_minutes、next_run_at，来源为内存中的调度器状态实时计算
- **调度统计汇总**: 推送/提取的总次数、成功数、失败数、成功率，由历史表聚合得出

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 用户在 5 秒内打开调度面板并看到所有定时任务的运行状态和下次执行时间
- **SC-002**: 用户能通过面板直观判断推送任务的成功率（无需查询数据库或日志）
- **SC-003**: 调度任务停止运行时（如配置错误导致），用户在 1 分钟内通过面板发现（下次执行时间异常或停止状态），而非等待数小时靠日志排查
- **SC-004**: 面板的下次执行时间倒计时准确率 100%（与实际执行时刻偏差小于 30 秒）
- **SC-005**: 推送失败记录的可视化使失败率超过 20% 的时间段在 1 次面板浏览内被识别

## Assumptions

- `/api/status` 接口已返回 `schedulers` 块（含 push/extract 的 running 和 next_run），面板可复用此数据源
- `push_histories` 表已存在且数据完整，无需新建迁移
- 提取历史需新建 `extract_histories` 表（迁移 009），记录每次提取批次结果
- 下次执行时间的实时计算逻辑可在后端 misc.rs 的状态接口中完善（修正重启后的计算偏差）
- 面板作为独立路由页面 `/scheduler` 或 Dashboard 的扩展区块，由实现阶段决定具体位置
- 调度状态刷新采用轮询方式（如每 30 秒拉取一次 /status），暂不引入 WebSocket 实时推送（属未来增强方向）
- 提取历史记录在每次提取批次执行成功后写入，失败时也记录（status=failed）
